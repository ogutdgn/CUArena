# Equation — Insert > Symbols

## What real Word does
Insert > Symbols > **Equation** is a split button. The top half (or **Alt+=** / Alt+Shift+=) inserts an empty math zone ("Type equation here") at the caret and switches into the equation editor, raising the **Equation** contextual tab (older builds: "Equation Tools | Design"). The bottom-half dropdown opens the **Built-In** gallery (~9 named equations: Area of Circle, Binomial Theorem, Expansion of a Sum, Fourier Series, Pythagorean Theorem, Quadratic Formula, Taylor Expansion, Trig Identity 1/2) plus **Insert New Equation**, **More Equations from Office.com**, **Ink Equation…**, and **Save Selection to Equation Gallery…**.

The **Equation** contextual tab carries four groups: **Tools** (mini-gallery, Professional / Linear / Normal Text, the **Convert ▾** notation dropdown — Unicode (UnicodeMath) / LaTeX, to-Professional/to-Linear, All/Current — and the Equation Options launcher); **Symbols** (a scrollable math-symbol mini-gallery with category subsets: Basic Math, Greek, Letter-Like, Operators, Arrows, Negated Relations, Scripts, Frakturs, Double-Struck, Geometry); and **Structures** (11 template galleries: Fraction, Script, Radical, Integral, Large Operator, Bracket, Function, Accent, Limit and Log, Operator, Matrix).

OOXML: every equation is stored as **Office Math Markup Language (OMML)** under the `m:` namespace (`http://schemas.openxmlformats.org/officeDocument/2006/math`). Inline math is `<m:oMath>`; display (own-paragraph) math is `<m:oMathPara><m:oMathParaPr/><m:oMath>…</m:oMath></m:oMathPara>`. Professional vs Linear is only a UI display mode — the saved tree is identical. Structures map to concrete elements: fraction `<m:f>`, radical `<m:rad>`, n-ary `<m:nary>`, super/sub `<m:sSup>/<m:sSub>/<m:sSubSup>/<m:sPre>`, delimiter `<m:d>`, function `<m:func>`, accent `<m:acc>`, limit `<m:limLow>/<m:limUpp>`, matrix `<m:m>`, equation array `<m:eqArr>`. **Ink Equation** opens a handwriting canvas (Write/Erase/Select-and-Correct/Clear + live Preview) and commits to the same OMML (no ink retained). **Save Selection to Equation Gallery** stores the selection as a building block (`w:docPart`/`w:docPartObj` in the glossary document).

## Current clone state
**shallow** — `H.equation` (commands.js:428) opens `WC.Dialogs.equation()` (dialogs.js:85): a textarea + 6 Unicode-math preset chips; Insert calls `WC.PM.insertEquation(text)` (bridge/insert.ts:177), which inserts **plain text styled Cambria Math + italic** via `insertContent` — explicit `KNOWN DEVIATION: equation = Cambria Math italic styled text, NOT OOXML <m:oMath>` at insert.ts:181. The dropdown `equationMenu` (commands.js:509) renders only 5 hardcoded preset strings + "Insert New Equation"; the advertised **Ink Equation…** and **Save Selection to Equation Gallery…** items (ribbon-data.js:925-926) are never rendered and have no handler; the **Alt+=** shortcut (ribbon-data.js:920) is unwired (app.js:96 binds only Ctrl+= to zoomIn). No Equation contextual tab (ribbon.js, state-sync.ts has no equation-context detection).

**Important engine fact (verified, not in the grounding repo summary):** the fork ALREADY ships a full OMML subsystem that the bridge does not use. Real `<m:oMath>`/`<m:oMathPara>` **import** → `mathInline`/`mathBlock` PM nodes (`v2/importer/math/math-importer.js`); the nodes are registered in the live editor (`extensions/math/{math-inline,math-block}.js`, listed at `extensions/index.js:137-138`); the paged engine **renders** them as browser MathML (`_vendor/.../painter-dom/src/runs/math-run.ts` → `features/math/omml-to-mathml.ts`, a ~20-converter registry: `m:f`, `m:rad`, `m:nary`, `m:sSup`, `m:d`, `m:func`, `m:acc`, `m:m`, `m:eqArr`, …); the layout-adapter emits a `MathRun` (`core/layout-adapter/converters/math-block.ts`); and **export** round-trips the OMML verbatim via the passthrough exporter (`v2/exporter/math-passthrough.test.js` locks `originalXml` deep-copy + child order). So real OMML math already imports, paints, and saves — only the *authoring* path (insert/edit) is the styled-text fake.

## Can we build it in our engine?
**Verdict:** 🟡 Buildable with additive fork edits
**Why:** The hard part — an OMML node type, a paged renderer, and a round-tripping exporter — **already exists and is wired into the live editor** (`mathInline`/`mathBlock` at `extensions/index.js:137-138`; `omml-to-mathml.ts`; `math-passthrough` exporter). Inserting a *real* equation is therefore NO-FORK: build an OMML JSON tree (`{name:'m:oMath', elements:[…]}`) and `editor.chain().insertContent({type:'mathInline', attrs:{originalXml, textContent}})` — the existing import/render/export path takes it from there, replacing the Cambria-Math-text fake. What is NOT free: (1) a **UnicodeMath/LaTeX → OMML build-up parser** (to turn `a/b`, `x^2`, `\sqrt`, `\int` into the `m:f`/`m:sSup`/`m:rad`/`m:nary` JSON) — the structures/Symbols galleries need this; none exists. (2) **In-place 2-D editing** — `mathInline`/`mathBlock` are PM `atom` nodes (no editable interior), so the Equation contextual tab's Professional/Linear/Convert and structure-placeholder editing have no host; a real editor is a new authoring surface. (3) **Ink Equation** needs a handwriting-to-math recognizer (external runtime we don't have). (4) **Save to Gallery** needs the building-blocks/`docPartObj` subsystem (absent). The "additive fork" tag covers small touches if the OMML JSON builder is colocated with the math extensions; the *insertion plumbing itself* is NO-FORK.

## Required structures to build it
- **PM node/extension:** reuse the existing `mathInline` / `mathBlock` nodes (`superdoc-fork/extensions/math/`) — already registered. (For an editable equation editor: a NEW interactive node/NodeView is required — large.)
- **Converter handler (super-converter):** exists — import at `v2/importer/math/math-importer.js`; export via passthrough (`exporter.js` `translatePassthroughNode`, locked by `v2/exporter/math-passthrough.test.js`). The v3 `w/oMath/oMath-translator.js` is only a boolean stub; the real path is v2 passthrough on `originalXml`. **No new handler needed for insertion** of pre-built OMML.
- **OOXML target:** `m:oMath` (inline) / `m:oMathPara` (display), with structure children `m:f`, `m:rad`, `m:nary`, `m:sSup`/`m:sSub`/`m:sSubSup`/`m:sPre`, `m:d`, `m:func`, `m:acc`, `m:limLow`/`m:limUpp`, `m:m`, `m:eqArr`.
- **Bridge verb(s):** replace `WC.PM.insertEquation` (insert.ts:177) so it inserts a real `mathInline`/`mathBlock` node from an OMML JSON tree instead of styled text; add a small OMML-builder module (preset gallery → OMML JSON; optionally a UnicodeMath→OMML parser for typed input).
- **Fork edit?** additive (OMML JSON builder can live beside `extensions/math/`; insertion via `insertContent` touches no fork internals — that part is NO-FORK). A full editable equation editor would be a larger, non-additive new subsystem.
- **Rough size:** **M** for "gallery presets insert as real OMML + round-trip" (the high-value win). **XL** for the full Word equation editor (build-up parser + 2-D editing + contextual tab + galleries). **Ink Equation = ⛔ external runtime; Save-to-Gallery = L (new building-blocks subsystem).**  •  **Dependencies:** rides the already-shipped OMML import/paint/export pipeline; the editor variant would need a new authoring/NodeView surface.
